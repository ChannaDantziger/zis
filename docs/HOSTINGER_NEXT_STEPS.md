# המשך עבודה: Git, Hostinger ונתונים חיים

[אינדקס](PLAN_INDEX.md) · [קובצי Docker](HOSTINGER_DOCKER_PREVIEW.md) · [משימות בעלת האתר](OWNER_ACTIONS.md) · [תוכנית המימוש](IMPLEMENTATION_PLAN.md).

עדכון 19.11.2026: בעלת האתר מאשרת נתוני חנות אמיתיים ומדווחת שבדקה ידנית את מסד הנתונים והתמונות והכול תקין. היקף הבדיקה לא פורט ולא אומת עצמאית. המשתמשים יעדכנו נתוני אמת באותו מסד שישמש בהמשך ב־Production. סביבת הניסוי והמסד אינם מבודדים; עדכון או מחיקה בניסוי משפיעים על נתונים חיים. תפעול ההזמנות ייבדק לאחר פריסה ב־Hostinger. הסדר אינו מהווה אישור למסלול תשלום או להשקה.

## 1. גיבוי לפני בדיקות כתיבה

1. בעלת האתר נכנסת ל־Supabase ובוחרת את הפרויקט הפעיל. ב־**Database → Backups** בודקת האם קיימים גיבויים, תאריך הגיבוי האחרון, תדירות ויכולת שחזור לפי תוכנית החשבון. לפי [תיעוד Supabase](https://supabase.com/docs/guides/platform/backups), גיבוי אוטומטי תלוי בתוכנית; בחשבון Free יש לתכנן ייצוא עצמאי.
2. לוודא גיבוי נפרד של תמונות וקובצי Storage: גיבוי מסד הנתונים כולל metadata ולא את הקבצים עצמם. לקבוע מקום מוגן, תדירות ואחראית, ולנסות שחזור קובץ בסביבה מבודדת. לא למחוק או לדרוס תמונות כדי לבצע בדיקה.
3. ב־Hostinger → VPS → Manage → **Backups & Monitoring → Snapshots & Backups** לבדוק גיבוי שרת זמין. snapshot ידני עשוי להחליף snapshot קיים ולפוג; יש לקרוא את הפרטים לפני יצירתו. גיבוי VPS אינו גיבוי Supabase החיצוני. [Hostinger](https://www.hostinger.com/support/1583232-how-to-back-up-or-restore-a-vps-at-hostinger/).
4. לתאם תרגיל שחזור בסביבה נפרדת; אין לשחזר על המסד הפעיל לצורך בדיקה. פיתוח מכין נוהל ואימות לפי סוג החשבון; בעלת האתר מאשרת אחראית ותדירות.

## 2. Git ובדיקת בנייה

קובצי Docker ו־Workflow הוכנו מקומית; Docker אינו מותקן במחשב הפיתוח ובניית images טרם אומתה. בענף העבודה יש גם שינויים מקומיים עסקיים אחרים. פיתוח יסדר PR ממוקד עם תכולת שחרור נבחרת, יבדוק את ה־diff והקבצים הנדרשים, ואז יפעיל GitHub Actions לבניית שלושת ה־images. אין להשתמש ב־`git add .` כדי לא לצרף שינויים שאינם קשורים. ה־PR יכלול קוד בהתאם להתחייבויות השרת והמסד; הוא אינו אישור להשקה.

בעלת האתר בודקת ב־GitHub ש־ruleset ל־`production` פעיל ונאכף. המאגר נצפה כ־Public, אך אכיפת הכלל לא אומתה. פיתוח מטפל בשגיאות build ומדווח תוצאות. רק לאחר review ו־CI תקין מקדמים PR ל־`master` ואחריו PR שחרור ל־`production`.

## 3. חיבור ותצוגה ב־Hostinger

הוראות שמות ה־Secrets וה־Variables ב־[HOSTINGER_DOCKER_PREVIEW](HOSTINGER_DOCKER_PREVIEW.md). בעלת האתר מזינה את הערכים ישירות ב־GitHub Settings → Secrets and variables → Actions; פיתוח אינו מבקש ערכים בצ'אט. יש להגדיר בנפרד את תוקף אישור ההזמנה המאושר; אין ערך אוטומטי כמדיניות עסקית.

פיתוח מאמת את תצורת Hostinger, גרסת Action, Docker Compose והפעלת שירותים; יש לוודא גיבוי, ruleset ו־CI לפני הפעלת `HOSTINGER_DEPLOY_ENABLED`. לאחר מיזוג השחרור, ה־Workflow מופעל ב־push ל־`production`. אין עדיין HTTPS ציבורי או דומיין, ולכן תצוגת הבדיקה זמינה דרך מנהרת SSH בלבד לפי המדריך; הפורטים קשורים ל־loopback ב־VPS.

## 4. בדיקת תפעול הזמנות לאחר פריסה

בעלת האתר ופיתוח בודקים יחד מול האתר ב־Hostinger: הצגת מוצר אמיתי ותמונה, מחיר ומלאי; יצירת הזמנת ניסיון מזוהה, הצגתה בניהול, הכנה, אריזה, אספקה וביטול לפי מה שממומש. מתעדים מספר הזמנת ניסיון ותוצאות בלי פרטים אישיים. מסלולי תשלום אמת נבדקים רק לאחר חיבור ספק ותיאום מתאים; מצב ניסיון או תשלום חיצוני אינו הוכחה לסליקה. מאחר שזה DB משותף, כל שינוי בהזמנה/מלאי הוא אמיתי ולא נמחק אוטומטית; מתקנים נתוני ניסיון רק דרך תהליך מאושר.

## 5. ניטור והשלמה לפני חשיפה ללקוחות

פיתוח מכין בדיקות health/readiness, ניטור זמינות, התראות על כשל ותיעוד לוגים מסוננים. בעלת האתר קובעת מי מקבלת התראה, ערוץ וזמן תגובה. יש לוודא שבדיקות מחוץ ל־VPS אינן חושפות את סביבת הניסוי הסגורה. ל־Production ציבורי נדרשים כתובת HTTPS תקינה, proxy, CORS, בדיקות נגישות ומסלולי לקוחה ותפעול, שחזור שנוסה ודרך חזרה לגרסה. לפי P8, חוסר בידוד סביבת DB נשאר פער מתועד גם לאחר החלטת השימוש המשותף; אין לסמן Staging מבודד כמאומת.

## מה נשאר פתוח

- שם התוכנית ב־Supabase, מצב/תדירות גיבוי DB ותמונות ואחראית גיבויים אינם ידועים.
- אכיפת ruleset, build Docker וגישת SSH/VPS טרם אומתו.
- כתובת HTTPS, הגדרת ניטור והוכחת שחזור טרם הושלמו.
- תפעול הזמנות, תשלום ותנאי P8/P9 ממתינים לבדיקות ולאישור ההשקה.
