# תוכנית העלאה לפרודקשן — Git, Docker ואירוח

[README](../README.md) · [אינדקס מרכזי](PLAN_INDEX.md) · [P8/P9](IMPLEMENTATION_PLAN.md) · [תוכנית מסירה טכנית](planning/DELIVERY_AND_DOCUMENTATION.md) · [משימות בעלת האתר](OWNER_ACTIONS.md).

**מעמד:** תוכנית עבודה; נכון ל־17.11.2026 לא נמצאו במאגר Dockerfile, Compose או CI, והאירוח טרם נבחר. לכן אין כאן הוראות פקודה לספק מסוים ואין טענה שהמערכת מוכנה לעלייה. התוכנית מניחה Git כניהול קוד, Docker לאריזה, Registry להעברת image אם ספק האירוח דורש זאת, ושירות Hosting להרצת הקונטיינרים.

## תמונת תהליך

1. משלימים שערי מוכנות מוצר ו־Production.
2. בוחרים ספק אירוח, סביבות, דומיינים ועלויות.
3. הסוכן מכין קוד פריסה בטוח, CI ותיעוד.
4. מעלים שינוי ל־Git ומקבלים Build/בדיקות.
5. בונים ומפרסמים Docker image מתויג ל־Registry או בונים אצל ספק האירוח.
6. מגדירים Staging, סודות ושירותים, ופורסים גרסה לבדיקה.
7. מריצים קבלה עסקית וטכנית; מתקנים וחוזרים על הפריסה לפי הצורך.
8. בעלת האתר מאשרת מועד השקה; פורסים Production, מאמתים, ומכינים חזרה לגרסה קודמת.
9. משלימים תיעוד, ניטור, גיבוי ותרגיל שחזור.

Git הוא מקור הקוד וההיסטוריה. Docker image הוא תוצר בנייה בלתי משתנה. Registry מאחסן/מעביר תוצרים; הוא אינו אתר החנות. Hosting מריץ את ה־API ואת יישומי ה־Frontend. אין חובה להשתמש ב־Docker Hub: משתמשים ב־Registry המובנה של הספק או בשירות שנבחר. GitHub/GitLab ושמות ספקים הם דוגמאות בלבד, לא בחירה שכבר נעשתה.

## חלוקת אחריות

| הסוכן יכול לבצע במאגר | בעלת האתר/המשתמשת מבצעת או מאשרת בחשבונות חיצוניים |
|---|---|
| לבדוק את מבנה הפרויקט והפקודות; להשלים Dockerfile/Compose ו־`.dockerignore`; לבנות תצורת Production ללא סודות; להכין Workflow של CI/CD, health checks, תיוג גרסאות ו־Runbook; לסקור הגדרות ולהסביר כל שדה; לתקן קוד בעקבות כשלים; להכין תוכנית חזרה לאחור. | לבחור ספק/תוכנית/תקציב; לוודא בעלות וגישה ל־Git, Registry, Hosting, DNS, DB ו־Storage; ליצור חשבונות/משתמשים והרשאות; להזין סודות ישירות במנהל הסודות של הספק; לאשר עלויות, דומיינים, פרסום ומועד השקה; לבצע או לאשר פעולות החשבון וה־DNS; לבדוק את החנות והניהול בפועל ולדווח תוצאות. |

הסוכן יכול לבצע פריסה רק לאחר שקיבל כלי/הרשאה מתאימים לחשבון ובקשה מפורשת לפעולה החיצונית. אין להעביר סיסמאות, מפתחות, כתובות חיבור עם סיסמה או קובצי `.env` לצ'אט. אין לקרוא, לחפש או לצרף קובצי `.env`; `.env.example` בלבד הוא תבנית מותרת. אין לכתוב סודות ל־Git, Docker build args, image, לוגים או מסמכים.

## שלבים מפורטים

### שלב 0 — לוודא שהמוצר מוכן לפריסה

**הסוכן:** קורא את [תוכנית המימוש](IMPLEMENTATION_PLAN.md), [פערים פתוחים](OPEN_ISSUES.md), דוחות האימות והחוזים. מכין רשימת חסמים לפי מסלול לקוחה, API, ניהול, DB, תמונות, תשלום ותפעול. בודק שה־build וה־scripts המוצהרים תואמים לקבצים. אינו מסיק שמערכת מוכנה כי מסך נראה תקין או כי בדיקות מקומיות עברו.

**בעלת האתר:** מספקת תוכן וערכי עסק מאושרים, בוחרת החלטות שנותרו פתוחות, ומארגנת בדיקות U13 מול Staging כאשר יהיה זמין. אינה מוסרת סודות.

**תוצר/שער מעבר:** רשימת חסמים עם אחראי ותנאי סגירה. לפי מדיניות המאגר, חנות אינה נחשבת מוכנה לשחרור עד שיש מסלול לקוחה ותפעול מלאים לפי `IMPLEMENTATION_PLAN.md`; פריסה מוקדמת אפשרית רק כ־Staging מסומן, לא כהשקה. [תוצר שלב 0 שנבדק ב־17.11.2026](PRODUCTION_READINESS_PHASE_0.md).

### שלב 1 — בחירת מבנה Git וחשבונות

החלטת ענפים ופקודות לביצוע מתועדות ב־[מבנה Git ו־PR לפרודקשן](PRODUCTION_GIT_BRANCHES.md): `master` לאינטגרציה, `production` כמקור הפריסה המתוכנן ל־Hostinger, ו־PR מאושר ביניהם. טרם נוצר ענף production או חיבור Hosting.

**הסוכן:** מציע מבנה ענפים וזרימה פשוטה, כגון PR לענף ראשי ותג גרסה לכל שחרור; מציע הגנת ענף, בדיקות חובה, הרשאות מינימליות ו־Registry מתאים. יוצר את קובצי ההגדרה רק לאחר שהיעד ידוע. מכין רשימת חשבונות/הרשאות ותרשים זרימה `Git → CI → Registry → Hosting`.

**בעלת האתר:** בוחרת/מאשרת Git provider וארגון/מאגר, Hosting ושירותי DB/Storage, Registry אם נפרד, תקציב וחיוב, אזור שרת, מספר סביבות ומי רשאי לבצע Deploy. מפעילה אימות רב־שלבי ומזמינה משתמשים לפי צורך.

**תוצר/שער מעבר:** שמות ספקים ותוכניות, בעל חשבון אחראי, פרטי גישה מוגדרים בחשבונות עצמם, והחלטה האם בניית Docker נעשית ב־CI או אצל Hosting. לשמור במסמך רק שמות משתנים/שירותים וכתובות ציבוריות; בלי ערכי סוד.

### שלב 2 — תכנון כתובות, רשת ותצורה

**הסוכן:** ממפה שירותים נפרדים: API, Storefront, Admin, DB ו־Storage. מציין משתני סביבה לפי צד לקוח/שרת, בדיקות readiness, CORS, מגבלות גוף/זמן, מדיניות cookies/session, כתובות חזרה ל־OAuth/Webhook לפי הספקים שנבחרו. מוודא שהגדרות לקוח הן ציבוריות בלבד ושאין לחשוף מפתחות שרת בבניית Frontend. מתכנן HTTPS, health endpoint, לוגים מסוננים ו־timeouts.

**בעלת האתר:** בוחרת ומחזיקה דומיין, מחליטה כתובות ציבוריות ל־store/admin/api, מאשרת אם Admin תחת כתובת נפרדת, ומוודאת גישה ל־DNS. מוסרת לסוכן רק שמות כתובות ציבוריות כשנדרשים; פרטי חשבון נשארים אצל הספק.

**תוצר/שער מעבר:** טבלת שירות→כתובת→פורט/בדיקת חיים→משתני תצורה (שם בלבד)→בעלים. ה־DB וה־Storage אינם משתמשים בדיסק הזמני של קונטיינר. תעודות HTTPS, CORS וכתובות callback ייבדקו ב־Staging.

### שלב 3 — להכין Docker וקבצי פריסה

**הסוכן:** מוסיף לפי המבנה בפועל Dockerfile רב־שלבי ל־API ולכל Frontend שנפרס בנפרד, תמונות בסיס נתמכות ומקובעות, משתמש ללא root, התקנה לפי lockfile, כיבוי מסודר ו־health checks. מוסיף `.dockerignore` שמונע הכללת `.env*`, `node_modules`, Git, קבצי בדיקה/תוצרי ביניים ומידע מקומי. מוסיף Compose לפיתוח/בדיקה מקומית בלי סודות Production, עם health dependencies ונתוני בדיקה בלבד. מוודא build סטטי של Frontend, ניתוב deep-link ו־refresh, ו־API URL נכון לכל סביבה.

**בעלת האתר:** מתקינה Docker Desktop רק אם תרצה להריץ קונטיינרים מקומית או אם יידרש לסוכן בסביבת העבודה. התקנה אינה דרושה אם CI/Hosting בונה את ה־image. מאשרת את שמות השירותים והתנהגות האתר, לא ערכי סוד.

**תוצר/שער מעבר:** קובצי בנייה והרצה, הוראות מקומיות, build נקי לכל שירות, בדיקת health/readiness, סריקת תכולת image/context לוודא שאין סודות, ובדיקה ש־Admin לא נכלל בחבילת Storefront. שלב זה אינו נוגע בסכמה או בנתוני Production.

### שלב 4 — Git ו־CI

**הסוכן:** מכין Workflow שמופעל ב־Pull Request ובתג/מיזוג לפי החלטת הענפים: התקנת תלויות בגרסאות lock, lint, typecheck, בדיקות קיימות, build, בדיקות תיעוד ו־Docker build. מוודא שכשל עוצר את התהליך. מגדיר הרשאות Workflow מצומצמות ו־secrets של CI רק אם נדרשים, ללא הדפסה ללוג. מתעד איך להפעיל מחדש Workflow ואיפה רואים כשל.

**בעלת האתר:** מחברת/מאשרת את המאגר לחשבון CI, מגדירה הגנת ענף ואישורים ב־Git provider, ומזינה tokens ישירות ב־Secret store של השירות אם נדרשים. בודקת שהודעת הכשל אינה מציגה ערכים רגישים.

**תוצר/שער מעבר:** PR לדוגמה עובר; PR עם כשל ידוע נחסם; אין פריסה אוטומטית ל־Production ממיזוג רגיל אלא אם זה אושר במפורש ותועד. אין להוסיף או להריץ בדיקות חדשות בלי בקשת המשתמשת; בביצוע בפועל פועלים לפי בקשה/אישור עדכני.

### שלב 5 — Docker image ו־Registry

**הסוכן:** מגדיר בנייה עם תג ייחודי ובלתי משתנה (commit SHA/גרסה), תוויות מקור, שמירת digest, ובניית כל שירות בנפרד. מוודא שלא נארזים סודות, שה־image אינו מכיל כלי פיתוח מיותרים, ומכין פקודות/Workflow push ל־Registry שנבחר. מגדיר מדיניות שמירה/מחיקה של גרסאות תוך שמירת גרסאות שנפרסו.

**בעלת האתר:** יוצרת Registry או מאשרת Registry מובנה, מעניקה הרשאת push ל־CI והרשאת pull ל־Hosting, ומגדירה חיוב/שמירת תוצרים. אינה שולחת token. אם Hosting בונה מ־Git ישירות, מאשרת מסלול זה ומתעדת את מזהה ה־build.

**תוצר/שער מעבר:** image לכל שירות עם tag ו־digest, המקושר ל־commit. אפשר לזהות בדיוק איזו גרסה רצה ולבנות אותה מחדש. `latest` לבדו אינו מזהה גרסה מספק.

### שלב 6 — הקמת Staging והגדרות סודיות

**הסוכן:** מכין רשימת משתנים לכל שירות לפי `.env.example` והקוד, מסמן public/server-only, חובה/אופציונלי, מקור, ותהליך החלפה. מכין שירותים, health checks, לוגים, מגבלות משאבים והתראות במידת התמיכה. מוודא שאין שיתוף סודות בין Development, Staging ו־Production; מגדיר Staging מול DB ו־Storage מבודדים או סביבת בדיקה מאושרת. מתעד rollback של יישום.

**בעלת האתר:** יוצרת את פרויקט/שירותי Staging, מזינה משתנים סודיים ישירות ב־Hosting Secret Manager, יוצרת מפתחות ייעודיים והרשאות מינימום, ובודקת עם בעל DB/Storage שסביבת Staging מבודדת. מאשרת כתובות Staging, חיוב והגבלות גישה. אין להזין נתוני לקוחות אמיתיים בסביבת בדיקה ללא אישור ומדיניות מתאימה.

**תוצר/שער מעבר:** שירותים מתחילים, `/health` חי ו־readiness מדווח אמת על תלויות קריטיות; אין סודות בקוד/לוגים; חנות/Admin/API מקושרים; אין תעבורה ל־Production DB בטעות. היעדר DB אינו מסומן כ־ready.

### שלב 7 — מסד נתונים ומיגרציות

**הסוכן:** בודק את היסטוריית המיגרציות והקוד, מכין מסמך preflight ותוכנית שינוי/התאמה לאחור, מזהה אילו שינויים נדרשים ל־Staging ול־Production ומכין SQL/מיגרציה לבדיקה. מתכנן גיבוי ו־verification שאינם משנים נתונים. לא מבצע ולא מפעיל מיגרציות, גם לא אוטומטית מתוך Docker, Compose, CI או startup.

**בעלת האתר:** מאמתת מצב/ledger מול ספק DB בתהליך המאושר, מתאמת גיבוי וחלון שינוי, ומריצה שינוי ידנית דרך workflow המאושר של ספק ה־DB או מבקשת מבעלת התפקיד המורשית. מדווחת לסוכן תוצאה ומזהה גרסה בלבד, ללא פרטי גישה.

**תוצר/שער מעבר:** אישור ידני מתועד לכל סכמה, בדיקה קריאה בלבד של גרסה/health, התאמת API לסכמה בפועל, וגיבוי זמין. אם אין ודאות מה הוחל, עוצרים; לא מריצים שוב מיגרציות על עיוור. זהו שער נפרד מפריסת קוד.

### שלב 8 — פריסה ל־Staging ובדיקות קבלה

**הסוכן:** פורס את ה־image המסומן אם הרשאה וכלי מתאימים או מספק צעדים מדויקים לבעלת האתר. מאמת לוגי startup/health, routes, CORS, TLS, headers, טעינת תמונות, קישורים ישירים ורענון, Login והרשאות. מסייע באבחון לפי קודי שגיאה/לוגים מסוננים. מתעד tag/digest, זמן, תוצאות ו־known issues.

**בעלת האתר:** מבצעת U13 בממשק: מוצר ותמונה, לקוחה/הזמנה ב־Sandbox, מייל/מסמך לפי האפשרויות, פעולות ניהול, הכנה/אריזה/אספקה, ביטול ותרחישי קצה. מאשרת כתובות/תוכן, נגישות ותצוגה בנייד/מחשב, ומדווחת תוצאה בלי מידע אישי או סוד.

**תוצר/שער מעבר:** רשימת קבלה חתומה עם ראיות ותיקונים; אין חיוב אמיתי ב־Staging; כשלים קריטיים נסגרים. לא עוברים להשקה על בסיס בדיקת health בלבד. פרטי כרטיס אמיתיים לא מוזנים במצב בדיקה.

### שלב 9 — אישור ופריסה ל־Production

**הסוכן:** מסכם גרסה מדויקת, תכולה, פערים, השפעה, שלבי פריסה, בדיקות smoke ותוכנית חזרה לאחור. בודק שיש גיבוי, ניטור, איש קשר, הרשאות ושה־Production secrets מוגדרים ב־Hosting. אחרי אישור ההשקה וההרשאה, פורס image מאומת לפי digest; לא בונה מחדש באופן לא מתועד באמצע הפריסה.

**בעלת האתר:** נותנת אישור סופי לגרסה/מועד, מבצעת את שינויי החשבון/חיוב/DNS או מאשרת ביצועם כשיש כלי גישה מורשה, זמינה לבדיקות וקובעת מי מטפל בתקלה. מאשרת שהזמנות אמיתיות ופתיחת החנות רצויות כעת.

**תוצר/שער מעבר:** deployment של גרסה מזוהה, DNS ו־HTTPS תקינים, smoke tests עברו, והבעלים אישרה את חוויית האתר. אם בדיקה קריטית נכשלת, עוצרים קידום/פתיחת מכירה ומפעילים חזרה לאחור לפי התוכנית. חזרת אפליקציה אינה מחזירה DB או מבטלת חיוב.

### שלב 10 — אימות אחרי עלייה, תפעול ושחזור

**הסוכן:** בודק readiness ונתיבים ציבוריים, לוגים מסוננים, זמינות API/DB, שגיאות לקוח/שרת, Webhook ותהליך תמונות לפי הרשאות. משווה גרסה פעילה ל־digest המאושר, מעדכן מדריכי פריסה, הפעלה, rollback ותקלות. מכין/מלווה תרגיל שחזור בסביבה מבודדת.

**בעלת האתר:** מבצעת רכישת בדיקה מאושרת שמתאימה ל־Production (ללא חיוב אמיתי אלא אם אושר), בודקת תפעול הזמנה, ממנה מקבלת התראות ומחליפה פרטי קשר/גישה של מי שעזב. מגדירה עם הספק תדירות ושמירת גיבויים, תקציב, RPO/RTO רצויים ומאשרת תרגיל שחזור.

**תוצר/שער סגירה:** דוח פריסה ותוצאות, גיבוי DB ומדיה ושחזור שנבדקו, ניטור והתראות עם אחראי, Runbook חזרה לאחור שנוסה, וקישורים מעודכנים בתיעוד. ממשיכים לעקוב אחרי כשלים/הזמנות חריגות במועד ההשקה.

## רשימת קבלה לפריסה

- [ ] מפת שירותים, ספקים, סביבות, דומיינים, בעלים ותקציב אושרה.
- [ ] מסלול חנות ותפעול עבר את תנאי `IMPLEMENTATION_PLAN.md`; חסמים שנדחו מתועדים.
- [ ] Docker build נקי; אין `.env`, `node_modules` או נתונים מקומיים בהקשר/image.
- [ ] CI עובר PR, נכשל באופן חוסם על תקלה, ו־push מוגבל להרשאות הנדרשות.
- [ ] image/tag/digest קשורים ל־commit וניתן לזהות/לשחזר אותם.
- [ ] Staging מבודד מ־Production; secrets מוזנים אצל ספק בלבד; readiness אמין.
- [ ] מצב DB ידוע; כל שינוי schema עבר תהליך ידני מאושר, גיבוי ואימות.
- [ ] HTTPS, DNS, CORS, deep links, Login, מדיה ו־Webhooks נבדקו ב־Staging.
- [ ] תרחישי קבלה עסקיים ופעולות ניהול הושלמו ותועדו.
- [ ] יש אישור בעלת האתר, גיבוי, ניטור, אחראי תקלות ותוכנית rollback.
- [ ] בדיקות אחרי עלייה, שחזור ותיעוד סופי הושלמו.
