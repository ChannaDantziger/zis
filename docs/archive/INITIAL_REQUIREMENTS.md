# ZIS — חנות מוצרי Sets

מסמך זה מתעד את הכיוון העסקי, הארכיטקטורה והדרישות הידועות עבור ZIS, חברת־בת של LIS, ואתר המכירות מבוסס React. זהו מסמך אפיון ראשוני, והוא יעודכן ככל שיתווספו החלטות ודרישות.

מסמך התכנון לשלב הבא נמצא ב־[NEXT_PHASE_PLAN.md](../../NEXT_PHASE_PLAN.md).

מסמך ה־ERD וסכמת בסיס הנתונים נמצא ב־[ERD_SCHEMA.md](../../ERD_SCHEMA.md), והוא מרכז את הטבלאות, הקשרים, האילוצים והאינדקסים הנדרשים.

השוואת ה־ERD מול האפיון נמצאת ב־[ERD_COMPARISON.md](../../ERD_COMPARISON.md), כולל טבלת הבדלים והחלטות שעדיין נדרשות.

תכנון ארכיטקטורת ה־Backend נמצא ב־[BACKEND_ARCHITECTURE.md](../../BACKEND_ARCHITECTURE.md), כולל מודולים, זרימות, API, אבטחה וטרנזקציות.

תכנון ארכיטקטורת ה־Frontend נמצא ב־[FRONTEND_ARCHITECTURE.md](../../FRONTEND_ARCHITECTURE.md), כולל Storefront, Admin Mobile-first, מסכים, מצב ו־API Client.

חלוקת הפרויקטים היא: `zis-db` למסד הנתונים והמיגרציות, `zis-api` ל־Backend, ו־`zis` ל־Frontend.

לאחר השלמת האב־טיפוס לפי כללי ה־Frontend וה־Design System יבוצעו תוספות הגלריה: תמונות אחידות, פתיחה מוגדלת ודפדוף בין התמונות.

האינדקס המרכזי של כל מסמכי התכנון וסדר המימוש נמצא ב־[PLAN_INDEX.md](../../PLAN_INDEX.md).

## מטרת המערכת

להקים חנות מקוונת נעימה, ברורה ונוחה לרכישה, עם:

- קטלוג מוצרים.
- מכירת כל מוצר כחלק מ־Set קבוע של מספר יחידות.
- תמונות מוצר באחידות ויזואלית.
- פתיחת תמונה בחלון Pop-up/Lightbox בלחיצה.
- עגלת קניות ותהליך Checkout פשוט.
- רכישה כאורח בשלב הראשון.
- אזור ניהול נוח להוספה, עדכון, הסתרה והסרה של מוצרים.
- ניהול הזמנות, משלוחים וסטטוסים.
- אפשרות להרחבה עתידית ללקוחות רשומים, חבילות, בוט ולקוחות עסקיים.

## החלטות שכבר התקבלו

### Frontend

- שימוש ב־React, רצוי עם TypeScript.
- חלוקה לקומפוננטות קטנות וברורות.
- CSS מסודר, עקבי וניתן לתחזוקה.
- התמקדות ראשונית בתצוגת Desktop, תוך שמירה על בסיס Responsive להמשך.
- אזור הניהול יתחיל בתוך אותו פרויקט, תחת נתיב כגון `/admin`.
- החלטה מעודכנת: אזור הניהול יהיה אפליקציית Frontend נפרדת, בכתובת נפרדת ובתכנון Mobile-first; הוא לא ייכלל בחבילת ה־Storefront הציבורית.

### Backend

- Backend נפרד מה־Frontend.
- API ברור עבור מוצרים, הזמנות, משלוחים וניהול.
- פעולות רגישות יתבצעו בצד השרת בלבד.
- מפתחות סודיים לא יישלחו לדפדפן ולא יישמרו בקוד.

### Database ו־Storage

- ההמלצה הראשונית היא Supabase.
- מסד הנתונים יהיה PostgreSQL.
- תמונות וקבצים לא יישמרו בתוך טבלאות ה־Database.
- תמונות יישמרו ב־Storage, וב־Database יישמרו הנתיב, ה־URL והמטא־דאטה.
- מיקום המידע אינו מגבלה בשלב הנוכחי.
- יש להשתמש ב־RLS ובהרשאות נפרדות לקריאה ציבורית ולפעולות ניהול.

### סליקה

- סליקה אינה חלק מהשלב הנוכחי של האפיון הטכני.
- בהמשך הסליקה תיבנה כשכבה מבודדת, כדי לאפשר החלפת ספק.
- יש להעדיף SDK או Hosted Fields שמאפשרים חוויית Checkout בתוך האתר.
- בשלב הראשון לא תהיה שמירת כרטיסי אשראי או אמצעי תשלום.

### משתמשים

- בשלב הראשון הרכישה תהיה כאורח.
- בשלב עתידי ניתן להוסיף חשבונות לקוח, היסטוריית הזמנות, מועדפים והמלצות.
- שמירת העדפות ונתוני לקוחות תיעשה רק עם הסכמה מתאימה.

## מודל המוצר

המוצר הנמכר הוא Set, ולא יחידה בודדת.

לדוגמה:

- מוצר: `שם מוצר`.
- גודל Set: 3 יחידות.
- מחיר: המחיר עבור כל ה־Set.
- תמונה ראשית: יחידה אחת.
- תמונה נוספת: המחשה של כל ה־Set.

### וריאציות

המערכת צריכה לתמוך בווריאציות של מוצר, כגון צבע, סוג, גודל או מאפיין אחר שיוגדר באפיון.

כל וריאציה עשויה להיות בעלת:

- שם ותווית תצוגה.
- תמונות שונות.
- מחיר שונה.
- מלאי נפרד.
- מזהה פנימי/Product Code נפרד.
- זמינות שונה.

החלטה לשלב התכנון הבא: יש לנהל מחיר, מלאי, תמונות ו־Product Code בנפרד לכל וריאציה כאשר קיימות וריאציות. מוצר ללא וריאציות ייחשב כבעל וריאציית ברירת מחדל אחת.

### כמויות רכישה

"כמות" מתייחסת למספר ה־Sets שהלקוח מוסיף לעגלה. אין מכירה לפי יחידה בודדת בשלב זה.

לדוגמה, אם מוצר נמכר ב־Set של 3 יחידות:

- כמות 1 = שלושה פריטים.
- כמות 2 = שני Sets, כלומר שישה פריטים.

אין בשלב הראשון מכירה חוזרת אוטומטית או מנוי.

## גלריית תמונות

דרישות הגלריה:

- כל התמונות יוצגו במסגרת אחידה.
- יחס התמונה בתצוגת הכרטיסים יהיה עקבי.
- יש להשתמש ב־`object-fit: cover` או במנגנון מוסכם אחר, בהתאם לאופי התמונות.
- לחיצה על תמונה תפתח Lightbox/Modal מעל המסך.
- בחלון הפתוח ניתן יהיה לסגור, לעבור בין תמונות ולשמור על נגישות מקלדת.
- לכל מוצר תהיה תמונה ראשית ותמונות נוספות.
- יש לשמור את סדר התמונות במסד הנתונים.
- יש לתמוך בעתיד בהחלפת תמונות מאזור הניהול.

מבנה מומלץ:

- `products` — נתוני המוצר.
- `product_variants` — וריאציות, מחירים ומלאי.
- `product_images` — תמונות, סדר, סוג תמונה ווריאציה קשורה.

## אזור ניהול

בשלב הראשון אזור הניהול יהיה חלק מאותו פרויקט, אך ייבנה כמודול נפרד.

יכולות מתוכננות:

- הוספת מוצר.
- עריכת מוצר.
- העלאת והחלפת תמונות.
- ניהול וריאציות.
- עדכון מחיר ומלאי.
- הסתרה זמנית של מוצר.
- הסרה קבועה מהקטלוג באמצעות Archive/Soft Delete.
- ניהול הזמנות.
- עדכון סטטוס הזמנה.
- ניהול תאריכי משלוח.
- ניהול יעד משלוח.
- הגדרת תוספת עלות משלוח.
- צפייה בלוג פעולות ניהול.

אין למחוק מידע עסקי חשוב פיזית ללא החלטה מפורשת. עדיפות לסטטוסים כגון:

- `draft` — טיוטה.
- `active` — מוצג וזמין.
- `hidden` — מוסתר זמנית.
- `sold_out` — אזל מהמלאי.
- `archived` — הוסר מהקטלוג.

## ניטור ו־Health Check

יוגדר Endpoint כגון `/health` שיבדוק:

- שה־Backend פעיל.
- שה־Backend מסוגל להתחבר ל־Supabase.
- שהשירותים הקריטיים זמינים.

בנוסף תוגדר מערכת ניטור שתשלח התראה במקרה של כשל. בדיקת בריאות היא כלי לניטור אמינות, ולא צריכה להחליף תכנון Production או לשמש כפתרון יחיד למניעת הקפאת שירותים.

## Deployment ועלויות

אפשרות התחלתית בעלות נמוכה:

- Frontend סטטי ב־Render Static Site, Vercel, Netlify או Cloudflare Pages.
- Backend קטן ב־Render Web Service או שירות Serverless אחר.
- Database ו־Storage ב־Supabase.
- דומיין עצמאי עם SSL.

Render הוא ספק ענן ספציפי, ולא שם כללי לשרת. יש לו מסלול חינמי ומסלולים בתשלום. שירות Backend חינמי עשוי להיעצר לאחר חוסר פעילות, ולכן הוא מתאים בעיקר לפיתוח או לשלב ראשוני מאוד. ניתן לשדרג בהמשך או לעבור לספק אחר.

כדי לשמור על אפשרות מעבר:

- להשתמש ב־Docker או Runtime סטנדרטי.
- לשמור את כל ההגדרות ב־Environment Variables.
- לא לשמור תמונות או מידע חשוב בדיסק המקומי של השרת.
- לתעד Deployment, גיבויים ומיגרציות.

## אבטחה

- אין לחשוף מפתחות Secret בצד לקוח.
- `SUPABASE_SERVICE_ROLE_KEY` מותר לשימוש בצד שרת בלבד.
- יש להפעיל RLS על טבלאות חשופות.
- פעולות ניהול ידרשו הרשאת Admin.
- יצירת הזמנה תבוצע לאחר בדיקת מחירים ומלאי בצד השרת.
- אין לסמוך על סכומים שמגיעים מהדפדפן.
- יש להוסיף Rate Limiting ו־Validation ל־API.
- יש לתעד הרשאות, גיבויים ומדיניות מחיקה/ארכוב.
