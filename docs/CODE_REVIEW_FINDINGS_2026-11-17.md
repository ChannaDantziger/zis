# ממצאי שלוש סקירות קוד — 17.11.2026

[אינדקס](PLAN_INDEX.md) · [תוכנית עבודה](IMPLEMENTATION_PLAN.md) · [פערים קיימים](OPEN_ISSUES.md).

## היקף ואופן אימות

הופעלו ברצף `zis-pr-review`, `zis-security-review`, `zis-flow-review`. הסקירה הראשונה השוותה את השינויים המקומיים ל־HEAD: ארבעה קובצי תיעוד ששונו, תוכנית פריסה חדשה ושלושה Skills חדשים. לא נמצא שינוי יישום מקומי בסבב זה, ולא נמצא ממצא תקלה קונקרטי בתיעוד החדש. הסקירות הבאות בדקו באופן ממוקד את API ההזמנות, אישור תשלום ניסוי, Checkout, הרשאות, הגבלת בקשות ומלאי הניהול. זו אינה סקירה ממצה של כל המאגר.

הראיות להלן הן קריאת קוד ותיעוד קיים בתאריך הדוח. לא הורצו בדיקות, דפדפן, הזמנה, תשלום או מיגרציה; לא אומת DB או Production. ממצאים שתועדו בעבר מסומנים בהתאם ולא מוצגים כבדיקה חיה חדשה.

## תיקונים נדרשים

### 1. גבוה — מגביל הבקשות עלול להכביד על השרת ולחסום מבקרים יחד

**ראיה:** [`rate-limit.ts`](../zis-api/src/middleware/rate-limit.ts) שורות 15–26 שומר `Map` של כתובות IP ומחליף מונה ישן רק כשאותה כתובת פונה שוב. אין מחיקה של כתובות שפסקו לפנות ואין מגבלת גודל. [`app.ts`](../zis-api/src/app.ts) שורות 79–88 מחיל את המגביל על כל הנתיבים, ללא הגדרת Proxy מפורשת בקובץ זה.

**למה לתקן:** לאורך זמן, כתובות חדשות משאירות רשומות בזיכרון עד הפעלת השרת מחדש. אם ה־API ירוץ מאחורי Reverse Proxy ו־`request.ip` יהיה כתובת ה־Proxy, לקוחות שונים עשויים לחלוק מכסה אחת של 120 בקשות בדקה ולקבל 429 בעת עומס רגיל. ההתנהגות המדויקת של `request.ip` תלויה בתצורת האירוח שטרם נבחרה.

**תיקון 17.11.2026:** נוסף ניקוי תקופתי של מונים שפג חלון הזמן שלהם; המדיניות נותרה 120 בקשות בדקה לכל `request.ip`. **נותר:** הגדרת Proxy מהימן ובדיקת כתובת הלקוח ייעשו לאחר בחירת ספק האירוח. לא הורצו בדיקות או בדיקת runtime.

### 2. גבוה — מסך „מלאי זמין” אינו כולל מוצרים פשוטים

**ראיה:** [`InventoryPage.tsx`](../apps/admin-mobile/src/pages/InventoryPage.tsx) שורות 16–18 טוען רק `/admin/inventory/variants`; שורות 35–40 מציגות רק וריאציות ואף מודיעות שאין וריאציות כשזו הרשימה ריקה. גם [`admin-inventory-read.routes.ts`](../zis-api/src/routes/admin-inventory-read.routes.ts) שורות 8–9 חושף כאן נתיבי וריאציות בלבד. לעומת זאת, [`test-payment.service.ts`](../zis-api/src/commerce/test-payment.service.ts) שורות 52–67 מפחית מלאי גם ממוצר פשוט. דוח [בדיקת הדפדפן מ־08.11](ORDER_TEST_BROWSER_REPORT.md) תיעד את התסמין בפועל באותו מועד.

**למה לתקן:** מנהלת אינה רואה במסך המלאי פריטים פשוטים שאפשר למכור ושמלאיים מופחת בהזמנה. רשימה ריקה עשויה להטעות בהחלטות מלאי ותפעול.

**כיוון תיקון:** להוסיף מסלול רשימה ופרטים למוצרים פשוטים למסך המלאי, או לשנות במפורש את תפקיד המסך והניווט כך שיפנה למלאי הפשוט בקטלוג. הבחירה בממשק היא החלטת מוצר; הבעיה של רשימה מטעה מאומתת בקוד. בדיקת דפדפן חדשה לאחר תיקון נדרשת.

### 3. חוסם השקה — מסלול הזמנה אמיתית נעצר ב־pending

**ראיה:** [`order.service.ts`](../zis-api/src/commerce/order.service.ts) שורות 19–25 יוצר הזמנה עם `paymentStatus: 'pending'`. [`app.ts`](../zis-api/src/app.ts) שורות 141–143 מחבר יצירת הזמנה ואישור תשלום **ניסוי** בלבד; [`test-payment.service.ts`](../zis-api/src/commerce/test-payment.service.ts) שורות 18–25 דוחה במפורש הזמנה שאינה `is_test`. [P6 בתוכנית](IMPLEMENTATION_PLAN.md) שורות 119–129 עדיין מסמן חיבור ספק, Webhook, מלאי ומסמכים כעבודה פתוחה.

**למה לתקן:** לקוחה יכולה להגיע לשלב יצירת הזמנה, אך אין בקוד שנסקר מסלול מאומת שמעביר הזמנה אמיתית לתשלום שהושלם ולהמשך תפעול. זהו פער מימוש ידוע, לא רגרסיה מהשינויים המקומיים.

**כיוון תיקון:** להשלים P6 לפי החלטת ספק ומדיניות כשל, כולל אימות Webhook, מניעת חיוב או הקצאת מלאי כפולים, מסמכים ובדיקות Sandbox. לא להשתמש באישור תשלום הניסוי כתחליף. נדרש אימות מקצה לקצה לפני השקה.

### 4. רגיל — הודעת מס ישנה נשארה במסלול Checkout — תוקן 17.11.2026

**ראיה בעת הסקירה:** `checkout.store.ts` הציג שהצעת מחיר חסומה עד להגדרת שיעור מס והתייחס לקוד `COMMERCE_TAX_NOT_CONFIGURED`. חיפוש בקוד `zis-api/src` לא מצא הפקה של הקוד; `readQuoteContext` קורא הגדרות משלוח, מלאי ומוצרים בלבד.

**למה לתקן:** אם שגיאת 503 ישנה או מיפוי שגוי יגיע ללקוחה, ההודעה תנחה את המנהלת לבצע הגדרה שכבר אינה שייכת למסלול ההזמנה. זו אי־התאמה מאומתת בין טקסט הקוד להחלטה המתועדת; לא אומת שהענף מופעל כעת.

**תיקון:** הוסר מיפוי ההודעה הישן והקוד הוסר מרשימת שגיאות 503 שמנקה ניסיון הזמנה. עודכנה בדיקת ה־Storefront שלא תצפה להודעת שיעור מס. לא הורצו בדיקות לאחר השינוי.

## סדר טיפול מומלץ

1. לקבוע ספק ומדיניות P6, ואז להשלים ולבדוק מסלול הזמנה אמיתית לפני השקה.
2. לתקן את מגביל הבקשות כחלק מהכנת האירוח ולבדוק אותו מאחורי ה־Proxy שנבחר.
3. להכריע איך מנהלת תראה מלאי מוצרים פשוטים ולתקן את מסך המלאי בהתאם.
4. לנקות את הודעת המס לאחר בדיקה אם קוד השגיאה עדיין אפשרי.

לא שונו קובצי יישום במסגרת הסקירה. הראיות כאן אינן מעידות ש־Production בטוח או שהחנות מוכנה לשחרור.
