# מלאי וסטטוסים — התנהגות הקוד הקיים

[אינדקס](PLAN_INDEX.md) · [מודל יעד](INVENTORY_MODEL.md) · [פערים](OPEN_ISSUES.md).
אומת בקריאת קוד ב־29.10.2026; התיאור מבדיל מימוש מקומי, מצב שאינו ממומש ומדיניות עסקית. חלק מהקבצים שנבדקו הם שינויים מקומיים לא ממוסגרים, לכן אין להסיק מהם מה פועל ב־Production.

## מלאי

- זמין ב־product_variants.available_sets, ביחידות Sets ולפי Variant.
- עדכון Admin מקבל delta שלם שאינו אפס וסיבה שאינה ריקה; יתרה שלילית נדחית.
- delta חיובי יוצר restock ושלילי adjustment.
- נשמרים before/after, סוג, סיבה, משתמש והזמנה; delta אינו שדה היסטוריה אחרי מיגרציה 004.
- getDefaultRestockQuantity קורא default_production_quantity_sets.
- עדכון והיסטוריה באותה טרנזקציה; אין כאן עדיין תזמור הזמנה מרובת פריטים.

## מכירה וחוסר — פער עסקי פתוח

### עדכון מדיניות 24.09.2026

- חוסר וזמינות הם לפי וריאציה בלבד. אין ליישם fallback או העברת מלאי בין וריאציות בלי פעולה מפורשת מחוץ להיקף זה.
- אחרי תשלום, שינוי פריט/כמות/כתובת והפרשי כסף מנוהלים מחוץ למערכת; ביטול בלבד עובר ב־Workflow. אחרי אריזה או יציאה הוא דורש החזקת חבילה, אישור נוסף ובחירת החזרת מלאי מפורשת.
- אלה החלטות יעד בלבד. הקוד המתואר להלן לא הותאם להן עדיין; אין להסיר הגנה ישנה או להוסיף החזרת מלאי בלי idempotency, Audit ובדיקות.

- applyPaidSale מיועד להיקרא אחרי תשלום, אך אינו מאמת payment_status שמור בעצמו.
- בקוד, חוסר ללא הסכמה גורם לחריגה.
- בחוסר מאושר נצרך המלאי הזמין; היתרה מוחזרת ב־shortage_sets עם shortage_accepted/deferred.
- הכלל הישן של דחייה מלאה הוחלף ב־22.09 בבחירת מדיניות בניהול, עם חסימת חוסר ידוע כברירת מחדל. השירות עדיין אינו מממש בחירה זו; O02.
- allocation מוחזר לקורא; השירות אינו שומר בעצמו את שורת ההזמנה או מקצה קיבולת שבועית.
- אין בשירות תהליך השלמת deferred או scheduler לעדיפות; זו דרישת יעד שטרם מומשה.
- reversePaidSale מוסיף את הכמות שסופקה ויוצר sale_reversal, בלי בירור צריכה או מניעת ביטול חוזר. יש להשלים O10.

## התראות

- כמות קטנה או שווה לסף יוצרת low_stock בקוד; יש ליישר ניסוחים עסקיים שאומרים “מתחת לסף”.
- חוסר מאושר יוצר inventory_risk, הכולל פרטי קשר מקלט הפעולה.
- Repository יוצר רשומה לכל Admin פעיל; אין שליחת Push בפועל.
- נדרשות הרשאות וגישה מצומצמת למידע ההתראה, ללא הדפסת פרטי לקוחות בלוגים.

## סטטוסים

- נשמרו ordered, in_preparation, packed, in_transit, delivered, approved, cancelled.
- canStartPreparation דורש paid ומצב השווה ל־defaults.preparationStatus.
- Default מתוכנן במיגרציה 003 הוא ordered. עדיין אין מסלול API לקריאת Default ולהתחלת הכנה.
- assertAdminCanCancel אינו חוסם approved/cancelled. לפי ההוראה האחרונה מ־22.09 ביטול אפשרי בכל שלב; O09 מתעד את התאמת החסימות הישנות לתהליך החדש עם שאלת החזקה בחבילה, אישור נוסף, טיפול כספי ומניעת כפילות.
- אין עדיין workflow מלא, עדכון סטטוס ב־DB או Audit מחובר.

## עץ בדיקת משלוח ומלאי — סקירת קוד 01.11.2026

העץ מתאר את הלוגיקה המקומית בלבד; לא אומתו DB או Production.

```text
טעינת Checkout → GET /delivery-dates ללא אזור
├─ החנות סגורה? → לא מוחזרים תאריכים.
└─ אחרת, לכל יום בטווח שהוגדר בודקים אזור זמן, טווח הזמנה ויום חלוקה מסומן,
   סגירות פעילות ו־cutoff להזמנה באותו יום. רק ימים שעברו את הבדיקות מוצגים.
   (בשלב הזה לא נקרא מלאי ולא נבדקת קיבולת ייצור ליום המסוים.)

אחרי בחירת תאריך ובדיקת פרטי העגלה → POST /availability ואז POST /quote
├─ העגלה עדיין נטענת/שגיאת טעינה/פריט חסר/כמות גדולה מהמלאי? → אין מעבר.
├─ /availability בודק פריט פעיל ובר־מכירה וכמות מול יתרת המלאי הנוכחית:
│  ├─ מוצר פשוט → availableSets = floor(products.available_items / products.set_size).
│  └─ וריאציה → product_variants.available_sets, שנמדד ב־Sets.
│  התאריך מוחזר בתשובה, אך אינו משנה את חישוב המלאי.
├─ /quote בודק שוב חנות, תאריך ומדיניות משלוח, מוצר/וריאציה פעילים,
│  מחיר ומלאי נוכחיים, מינימום סכום מוצרים וכלל משלוח מתאים.
└─ כל בדיקות האזור, התאריך, פרטי הלקוחה, המלאי וה־Quote עוברות
   וה־Quote תואם לעגלה הנוכחית? → כפתור "הבא" בשלב המשלוח זמין.

יצירת הזמנה ממתינה → השרת מחשב ומאמת שוב; מלאי אינו נשמר או מופחת.
לפני אישור תשלום ניסוי מורשה → השרת נועל ובודק מלאי שוב ומפחית אותו אטומית.
```

**הבחנה חשובה:** החלטת בעלת האתר מ־08.11: ימי האספקה והמלאי אינם תלויים באזור. בקוד המקומי `GET /delivery-dates` גלובלי ונקרא מראש; מ־19.11 `delivery-policy.ts` מאפשר כל יום שסומן בניהול, בכפוף לטווח, cutoff וסגירות. התאריך נקבע לפי מדיניות חנות כללית; אזור משמש כתובת ומחיר משלוח. המלאי נבדק לפי היתרה הנוכחית של מוצר/וריאציה, לא לפי קיבולת עתידית של יום האספקה. Quote והזמנה ממתינה אינם שומרים מלאי. אישור תשלום ניסוי הוא מסלול Admin בלבד; ספק סליקה אמיתי אינו מחובר. DB חי ודפדפן טרם אומתו לאחר השינוי.

**יחידות מלאי:** לפי החלטת בעלת האתר מ־01.11.2026, `products.available_items` סופר יחידות פיזיות; זמינות למכירה מעוגלת כלפי מטה ל־Sets שלמים. אישור תשלום ניסוי מפחית `quantity_sets × set_size_snapshot` יחידות פיזיות, וריאציות נשארות במלאי Sets. הזמנה פשוטה היסטורית ללא snapshot תקין נחסמת עם שגיאה מפורשת לבדיקה או ליצירה מחדש. המימוש המקומי עודכן; נדרשים typecheck ואימות DB מורשה כדי לאמת את ההתאמה לסכמה הפעילה.

### למה הכמות עלולה להיראות חסומה

- בעגלת הקניות, שדה הכמות מושבת בזמן `cartStore.isRefreshing` או כאשר הפריט סומן `missing`; ראו `apps/storefront/src/features/cart/CartItems.tsx`.
- הוספת כמות למוצר מוגבלת ליתרה שהגיעה מהקטלוג; `CartStore.addItem` מחזיר כשל אם הכמות המצטברת גדולה מהזמינות. בעגלה אפשר לערוך מספר גדול יותר, אך `canContinue` חוסם המשך עד שהכמות אינה עולה על המלאי.
- כפתור ההמשך במשלוח דורש אזור ותאריך תקפים, פרטי לקוחה שעברו ולידציה, Quote עדכני שתואם לתאריך/אזור/פריטים, ועגלה זמינה במלאי. שינוי בפרטים מבטל את ה־Quote ומחזיר את הכפתור לחסום עד לחישוב חדש.
- בהזמנה ממתינה אפשר לערוך כמות, להוסיף, להסיר או להחליף פריטים לפני תשלום; השמירה בודקת שוב מלאי ומינימום. דרושה מיגרציה 016 שהוכנה בלבד ולא הורצה. העדכון חוסם תשלום לאחר שינוי גרסה ומחייב טעינה מפורשת של פרטי ההזמנה העדכניים.
