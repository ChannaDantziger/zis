# מסך הבית הניהולי — מימוש וגבולות אימות

[אינדקס](PLAN_INDEX.md) · [תוכנית תפעול](planning/ADMIN_OPERATIONS_INTEGRATION_PLAN.md) · [פערים](OPEN_ISSUES.md)

עודכן 17.11.2026. מסך הבית וקיצורי דוחות ממומשים בקוד מקומי; אימות חי של כל הזרימות עדיין פתוח. מסך ההזמנות B1.2 נשאר הדגמה בלבד.

## מה חובר בקוד

- הנתיב `/` ב־Admin מציג דשבורד חדש: סיכומי היום, התרעות “דורש טיפול”, הזמנות לפי שלב, כמויות ייצור לפי קטגוריה/מוצר, הזמנות לפי עיר, מקום שמור לחוסרים וחריגים, ומשימות בתחתית.
- גרף השלבים קורא הזמנות לפי **תאריך אספקה של היום בישראל**. בחירת שלב מציגה את ההזמנות המרכיבות את המספר; בכרטיס של כל הזמנה מוצגת שורה לכל מוצר עם תמונתו, שמו ומספר הסטים. פרטי הזמנה פותחים תקציר לפי שלב ולאחריו נתוני הלקוחה, המשלוח, התשלום, הפריטים, הסכומים, ההקדשה, ההערות וההיסטוריה. אין שליפת פרטי אשראי.
- ייצור ועיר תומכים ביום נבחר או בטווח מן היום הנבחר ועד שבעה ימים אחריו, כולל שני הקצוות. לחיצה על כמות/עיר מציגה הזמנות, תאריכים וכתובות. ייצור מציג סטים שהוזמנו ושולמו (ללא ביטולים), ולצדם “נותרו להכנה” במצבי `ordered` או `in_preparation`.
- תמונות מוצר נשלפות מקשרי מוצר/וריאציה ב־DB ומקבלות URL חתום דרך Storage. בהיעדר תמונה נשמר שם המוצר ומוצג מקום ריק ברור.
- מעבר רגיל לשלב הבא פועל דרך API הסטטוסים הקיים. במעבר ל“נארזה” וביציאה למשלוח במסך הבית מוזן מספר מארזים; הוא נכתב עם שינוי הסטטוס, מופיע בפרטים ובשלב המשלוח. יציאה למשלוח ללא מספר מארזים שמור נחסמת בשרת.
- “פרטים נוספים” סגור כברירת מחדל. בתוכו בלבד אפשר לבחור שלב תפעולי לתיקון טעות; נדרש אישור נוסף. השרת בודק הרשאת מנהלת, תשלום, גרסת הזמנה, וכותב היסטוריית סטטוס ו־Audit. ביטול אינו חלק מהפעולה.
- ברכיב ההזמנות של הבית יש קיצורים לתוויות אריזה ולדוח יציאות של היום; ברכיב הייצור יש קיצור לדוח להדפסה של התאריך הנבחר. הדוחות נשארים מסכי צפייה/הדפסה נפרדים, וכל קיצור שומר את התאריך המתאים.
- משימות הבית מאפשרות יצירה חופשית, שלוש עמודות (פתוח/בטיפול/סגור), שינוי מצב והערה, והצגת כל ההיסטוריה. השינוי אפשרי גם למשימת מערכת קיימת; הרשאת מנהלת וגרסה נבדקות בשרת.

## API ושינוי מסד שהוכן

`GET /admin/home/orders?from=YYYY-MM-DD&to=YYYY-MM-DD` מחזיר רשומות לטווח עד שמונה ימים כולל. `GET/POST /admin/home/tasks` ו־`PATCH /admin/home/tasks/:taskId` מטפלים במשימות. `POST /admin/orders/:orderId/correct-status` מטפל בתיקון טעות. `GET /admin/orders/:orderId` הורחב לשדות העסקיים השמורים. כל המסלולים האלה למנהלת תפעול פעילה בלבד.

[מיגרציה 018](../zis-db/migrations/018_admin_home_tasks_and_packages.sql) מוסיפה `orders.package_count`, מצב משימה תלת שלבי וטבלת היסטוריית משימות. בעלת האתר דיווחה ב־10.11 שהחילה אותה ידנית והפעילה מחדש את החנות, הניהול וה־API. צילומי מסך של הבית מציגים טעינת גרפים ומשימה קיימת ללא שגיאת סכמה; ה־ledger והסכמה לא נבדקו ישירות מסביבת הפיתוח.

## אימות שבוצע ונותר

- `zis-api` build ו־`admin-mobile` typecheck/build עברו ב־10.11.2026.
- 14 בדיקות API ממוקדות ו־27 בדיקות Admin עברו; שתיים מבדיקות Admin משתמשות בהזמנות סינתטיות מבודדות ומוודאות שסכום הייצור והערים תואם לפירוט, כולל הזמנה ששולמה, נארזה, ממתינה לתשלום ובוטלה. בריצת API רחבה יותר עברו 153 מתוך 159 בדיקות; חמש בדיקות HTTP נחסמו בחיבור ל־`127.0.0.1` (`EACCES`) ואחת דולגה. גם ניסיון הרשאה מורחבת לא פתח את החיבור.
- שלושה צילומים ששלחה בעלת האתר ב־10.11 מציגים את המסך החדש מחובר: 0 הזמנות לתאריך הנבחר, משימה אחת פתוחה ונטענת בראש ובתחתית, וגרפים במצב ריק. זו ראיה חזותית לטעינה, לא לאימות ספירות של הזמנות או פעולות כתיבה.
- דפדפן סביבת הפיתוח לא הצליח להגיע לשרת המקומי (`ERR_CONNECTION_TIMED_OUT`/`EACCES`), וכלי בדיקת הסכמה בקריאה בלבד נעצר כי `DATABASE_URL` אינו מוגדר בסביבת הפיתוח הזאת. לא נקראו סודות או קובצי `.env`.
- בעלת האתר אישרה שאין כרגע יום עם הזמנות לבדיקה. לכן אין בדיקת פירוט הזמנה או תמונות מול נתוני אמת; לא נוספה הזמנת דמה למסד. כשיהיו הזמנות, יש לבדוק ספירת שלבים מול הפירוט, תמונות, יום/טווח מתגלגל, כתובות לפי עיר, פרטים מלאים, שמירת מארזים ותיקון טעות. בדיקת פתיחת משימה והיסטוריית הערות בממשק עדיין ממתינה לצילום. רק אז אפשר לסמן את מסך הבית כעובד בכל הזרימות ולהמשיך למסך הבא.

## גבולות ידועים

המסך מציג קטגוריה ותמונה לפי שיוך המוצר הנוכחי ב־DB; שם המוצר והווריאציה עצמם נשמרים כ־snapshot בהזמנה. תהליכי אריזה ותוויות במסכים האחרים לא עוצבו מחדש בסבב זה. “חוסרים וחריגים” נשאר מקום שמור לפי החלטת בעלת האתר. שינוי סטטוס תיקוני אינו מבטל/מחזיר מלאי או תשלום; תהליכי ביטול והחזר נפרדים.
