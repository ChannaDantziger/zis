## מסקנה ומעמד

**הבאג שוחזר ותוקן בקוד; 24 בדיקות PostgreSQL ו־3 בדיקות SQL מדומה עברו אחרי התיקון.**
לא נקראו קובצי סביבה, לא נשלחה בקשה לחברת אשראי, לא נוצרה הזמנה חיה ולא הורצה מיגרציה.

בשורה 34 של [test-payment.service.ts](../zis-api/src/commerce/test-payment.service.ts), ה־INSERT לתשלומים משתמש ב־`$1` לעמודת `order_id` מסוג UUID וב־`$1::text` לאסמכתה הטקסטואלית.
PostgreSQL דוחה את השאילתה בשלב קביעת סוגי הפרמטרים:

```text
SQLSTATE: 42P08
inconsistent types deduced for parameter $1
detail: text versus uuid
```

השירות המקורי נכשל גם כשההרשאה, הסכמה, המלאי, המחיר והתאריך תקינים.
הכשל שוחזר במוצרים פשוטים ובווריאציות. כתיבות מלאי ואישור שכבר בוצעו בטרנזקציה בוטלו יחד; ההזמנה נשארה pending.
זו סיבה מוכחת לחסימת אישור בקוד הנוכחי, התואמת לתסמין בדוח 08.11. אין הוכחה שהבקשה ההיסטורית הגיעה דווקא לשורה זו, כי לא נשמרה כאן תגובת השרת שלה.

## התיקון שנבדק

תיקון ממוקד הוחל בשאילתת התשלום:

```sql
-- כיום
values($1,'admin_test',$1::text,0,'paid',true,...)
-- התיקון שהוחל
values($1::uuid,'admin_test',$1::text,0,'paid',true,...)
```

ההמרה המפורשת ל־UUID מסירה את הסתירה. **לא נדרשת מיגרציה כדי לתקן את השאילתה הזאת.**
השירות שבקוד נבדק כעת ישירות מול PostgreSQL מקומי בזיכרון, בלי מתאם שמחליף את השאילתה.
הזמנת דוגמה בסך 270 ₪ עברה ל־paid עם תשלום מדומה של 0.00 ₪.
מלאי מוצרים פשוטים יורד מ־100/20 ל־96/8 לפי 4 ו־12 יחידות. ניסיון חוזר עם גרסה ישנה מחזיר את אותה הצלחה בלי כתיבה או הפחתה נוספת.

ממצא אבחון נוסף תוקן: `42P08` נמצא כעת ברשימת הקודים הבטוחים של [error-handler.ts](../zis-api/src/middleware/error-handler.ts).
הלוג שומר את קוד האבחון בלי לחשוף SQL, פרמטרים או פרטי לקוחה.

## סביבת הבדיקה וגבולותיה

השירות המקורי יובא באמצעות tsx; כל שאילתותיו הורצו על PostgreSQL 18.6 בתוך PGlite 0.5.16 בזיכרון.
[fixture.sql](../scripts/payment-review/fixture.sql) מגדיר סכמה סינתטית מצומצמת עם סוגי העמודות והאילוצים הרלוונטיים; הוא אינו מריץ או קורא מיגרציות ואינו מקבל מחרוזת חיבור.
הנתונים מלאכותיים, עם מזהים קבועים ושעון בדיקה קבוע לפני מועד האספקה. אין תלות ביום שבו מריצים את הבדיקה.

אין כאן אימות Supabase Auth/RLS, מסד Production או גרסתו, הרשאות חשבון המסד, תחרות בין חיבורים, מסכי דפדפן של החנות, או תהליך ההכנה עד המסירה.
PGlite משתמש בחיבור יחיד; הוכח retry סדרתי, לא עומס או מרוץ בין מנהלות.
לא נבדק חיוב אמיתי — מסלול הניסוי אינו מחובר לספק סליקה.

## שחזור והרצה

הנחת קדם: תלויות `zis-api` כבר מותקנות, כולל tsx. הפקודות מתיקיית המאגר:

```powershell
npm.cmd ci --prefix scripts/payment-review --ignore-scripts --no-audit --no-fund
npm.cmd --prefix scripts/payment-review test
npm.cmd --prefix scripts/payment-review run test:acceptance
```

כל הפקודות צפויות לעבור. בדיקת הקבלה מאשרת שהשירות עצמו מכיל את התיקון.
קובצי הבדיקה: [current-service.test.mjs](../scripts/payment-review/current-service.test.mjs), [candidate-service.test.mjs](../scripts/payment-review/candidate-service.test.mjs), [acceptance.test.mjs](../scripts/payment-review/acceptance.test.mjs).

הורדת npm מהטרמינל נכשלה ב־DNS גם לאחר אישור. החבילה הורדה מה־npm registry דרך הדפדפן, hash SHA-512 הושווה ל־integrity הרשמי, והיא חולצה לתיקיית node_modules של מעבדת הבדיקות בלבד. אין שינוי בתלויות היישום.
רקע על המנוע: [תיעוד PGlite הרשמי](https://pglite.dev/docs/).
