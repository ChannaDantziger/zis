# ZIS documentation review

Review documentation against the current repository and the user's requested scope. As part of this review, archive confirmed obsolete documentation versions under `docs/OLD` and update navigation as described below. Distinguish a candidate for removal from a file proven safe to remove; respect any narrower user instruction and applicable repository rules.

When requested as part of the complete code-review sequence, run this skill once after the other reviews and include its findings in the consolidated result. A direct request for a documentation review invokes this skill independently.

Start with `docs/PLAN_INDEX.md`, `docs/GUIDELINES.md`, `docs/IMPLEMENTATION_PLAN.md`, `docs/OPEN_ISSUES.md`, and `docs/OWNER_ACTIONS.md`, then read the relevant index entries, documents, and code. Follow `AGENTS.md` and its source-of-truth rules. Record review date, revision and dirty-worktree status; treat user changes and untracked files as potentially valuable.

For a project-wide request, inventory documentation and related artifacts across the repository, including indexes, README files, plans, operational guides, API/schema documents, HTML previews and supporting assets. Group by purpose and status: active guidance, implemented behavior, planned work, historical evidence, generated output, or unknown. Explicitly list excluded areas and formats. Do not assume an archive, older date, duplicate-looking filename, or missing inbound Markdown link makes a file unnecessary.

Check important claims against their best available evidence: current source and tests for local behavior, contracts and migration files for intended schema, scripts/configuration for runnable instructions, and approved decisions for policy. Treat migrations as files, not proof of their application. Mark production, external account, deployment and database state unverified unless independently verified in scope. Identify missing evidence, stale commands and paths, conflicting status or business rules, missing instructions, inaccurate examples and broken or misleading links. Follow claims across the relevant indexes and source documents. Do not resolve a business-policy conflict by inference.

For duplicate, obsolete or suspicious files, compare actual content and purpose, references from documentation, code, scripts, configuration and build/deployment assets, plus Git status/history where useful. Consider dynamic and external consumers and generated/source relationships. Report evidence, uncertainty, consequences, and a recommended action: retain, update, merge, mark historical, archive, or propose removal. Absence of a search hit alone is not proof of safe deletion; preserve historical records and user work until their purpose and dependencies are understood.

When a documentation version is demonstrably obsolete and its purpose and dependencies are understood, preserve it in `docs/OLD` with a clear historical/not-active notice and a link to its current replacement when one exists. Preserve useful content and existing user changes; for a document with a mixture of current and outdated guidance, prepare an accurate active replacement before archiving the old version. Update `docs/PLAN_INDEX.md` to identify the old file as historical, link its new path and the active replacement, and update `docs/DOCS_INDEX.md` when implemented-behavior navigation is affected. Repair incoming links and relative links within moved files; verify references from scripts, assets and code before moving. Do not overwrite an existing archive or move files whose status or dependencies are unclear: report them for further investigation. Never delete files as a consequence of this review alone. Respect existing `docs/archive` records and the instruction that archived plans are not execution instructions.

Run `scripts/check-docs.ps1` when applicable, and report its output and limitations: local structural checks do not establish semantic correctness, live status, HTTP availability, or heading-anchor validity. Use targeted code or tests only when they resolve a specific claim; record what was actually inspected and run. Do not claim exhaustive correctness without complete evidence. See [review checklist](references/review-checklist.md) for coverage and reporting guidance.

Report findings by impact, with document path and line, supporting or conflicting evidence, practical consequence, proposed fix and verification. Separately list candidate files and their recommended disposition with confidence and dependencies. Include coverage, date, checks, unverified claims and next steps; distinguish verified implementation, partially implemented, planned, historical and externally unverified. For a persisted report, follow the repository's Markdown size, index and issue-tracking rules. Never read, print, search, index or attach `.env` or `.env.*`; follow `AGENTS.md` file preparation rules and never run database migrations.
